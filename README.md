# 客服知识库试用环境

状态：本地试用环境可用；真实产品资料待补全。基于 MaxKB v2.10.6-lts，顶部导航已接入“客服知识录入”。使用可重建的前端覆盖层，后端与数据库结构未改动。

## 访问

- 管理后台：http://127.0.0.1:8088/admin/login
- 客服知识录入：http://127.0.0.1:8088/admin/customer-knowledge-intake （登录后在顶部点击“客服知识录入”）
- 演示产品 A：http://127.0.0.1:8088/chat/2062f16f60cfcac0/
- 演示产品 B：http://127.0.0.1:8088/chat/5f3371ce5a2e5bc5/
- 管理员账户：见 `.local/login.json`，初始默认密码已更换。

仅绑定本机地址，其他电脑当前不能访问。以上演示地址属于本次数据库实例，重新建库后的地址见 `.local/pilot.json`。

## 已配置

- 两个独立演示产品知识库，每个查询应用只绑定自己的知识库。
- 使用镜像自带的中文向量模型，不需要外部模型密钥。
- 相似度达到 0.75 时，直接返回知识原文，并显示来源；未命中时返回“暂无已确认答案，请登记待解答问题”。阈值仅为试用值，真实问答导入后需要以实际问题校准。
- 对话和知识保存在 PostgreSQL 中，Docker 持久卷为 `customer-support-pilot_maxkb-data`。
- 独立的“待确认区 · 不参与客服回答”。截图电池案例已导入，文档已停用，且未绑定任何查询应用。

这不是完整定制客服平台。当前用 MaxKB 应用区选择产品、用知识库维护问答；统一产品图片目录、自动创建待办、负责人指派、审批流、自动翻译尚未实现。

## 实际试用

1. 打开产品 A，输入“请问这个商品是什么型号？”，应得到 DEMO-A。
2. 打开产品 B，输入同一句问题，应得到 DEMO-B。

5. 在知识库中进入待确认区，查看 BATTERY-001。其产品身份和技术答案尚不完整。

## 自动生成知识库工作台

已增加一个本机录入工作台，用于把客服聊天、解决思路和截图整理成可审核的知识草稿：

```powershell
npm run intake
```

然后在 MaxKB 顶部点击“客服知识录入”，无需另开页面。8088 提供 MaxKB 导航，8090 是内嵌工作台依赖的本机服务，两者都需要运行。先在“模型设置”填写兼容 OpenAI Chat Completions 的多模态模型地址、模型名称和密钥，再在“录入知识”中选择产品智能体。工作台会读取智能体实际绑定的知识库，生成草稿后列出待补充信息；只有人工填写确认人并完成审核，才会写入并启用 MaxKB 文档。

建议第一版保持“一产品一智能体一知识库”。一个智能体绑定多个产品时，检索结果可能串用，工作台会禁止选择这类智能体，直到在 MaxKB 中调整绑定。API 密钥只保存在本机 `.local/generator.json`，不会写入知识库或返回到浏览器。

### 导航集成与重建

`integration/intake-view.js` 定义嵌入页面，`scripts/integrate-maxkb.mjs` 使用 AST 定位当前版本的路由表，加入菜单和页面，并复用原有布局与登录检查。生成的静态文件保存在 `.local/maxkb-integration/admin`，通过 `compose.override.yaml` 只读挂载。容器重启或重建后入口仍保留，镜像升级需重新适配。当前菜单仅向管理员展示；8090 仍是本机试用服务，不具备多人权限隔离。

首次在新机器重建时，先启动未挂载覆盖层的实例，再生成并应用：

```powershell
npm ci
docker compose -f compose.yaml up -d
npm run integrate:maxkb
docker compose up -d
npm run intake
```

运行 `node scripts/verify-intake-integration.mjs` 检查登录、顶部菜单、内嵌 API、刷新、前进后退和录入页布局。回退导航覆盖层可运行 `docker compose -f compose.yaml up -d`；不会删除知识库或录入草稿。

## 首批真实资料

将原始资料放入 `incoming/`，无需先整理成标准格式。先收集 5～10 个产品和 30～50 个历史案例：

- 产品图、名称、型号或 SKU，以及各店铺对应商品链接。
- 说明书和已经确认的售后处理方法。
- 客户提问、负责人回复、最终解决结果，保留完整上下文。

`templates/product.md` 是产品档案模板，`templates/answer.md` 是问答模板。原始截图位于 `sources/`，截图案例整理结果位于 `data/pending/BATTERY-001.md`。演示文档仅用于验收，不代表真实商品。

## 资料维护流程

1. 每个准确型号建立独立知识库；店铺不同但确为同款的产品共用一份档案。
2. 未解决的问题先保存为待确认区的文档，并保持停用。第一版由负责人手动整理，对话没有自动转成工单。
3. 负责人补全需要追问的信息、处理步骤和对客回复，留下确认人与日期。
4. 只将已确认内容添加到对应产品知识库，在文档设置中选择“直接返回”，启用文档，并等待向量化完成。
5. 查询应用仅绑定对应产品知识库，关闭问题优化，不配置生成模型，并设置无匹配时的固定答复。
6. 用新提问和相邻型号的提问做检索测试，确认没有误匹配后再给客服使用。

注：这些是试用阶段的人工维护约定，尚不是软件强制的审批权限。

## 启停与检查

在本目录运行 `docker compose up -d` 启动，`docker compose stop` 停止，`docker compose ps` 查看状态。不要删除持久卷，否则将删除数据库。

开发检查使用 Node.js 24：运行 `npm ci` 安装浏览器验证依赖；`npm run verify` 验证检索与产品隔离；`npm run verify:browser` 使用本机 Edge 验证电脑端对话。初始化新实例可运行 `npm run seed`，只添加缺失的演示资源，不覆盖现有答案。

## 已知限制

- 尚无已确认的真实产品问答，不能视为业务上线完成。
- 本地模型主要用于中文检索，尚未验证泰语原文直接检索；暂不自动翻译。
- MaxKB 手机端在 390px 视口测试中可返回答案，但出现 `offsetHeight` 和 `textarea` 空值错误；本轮推荐电脑端试用。用 `node scripts/chat-browser-check.mjs --mobile` 可复现，测试会如实报错。
- 上游 `knowledge/embedding_model` 接口返回缺少用户 ID；初始化脚本使用正常的 `model?model_type=EMBEDDING` 接口，不修改上游。若页面遇到相关模型选择问题，需要另行处理。

检查记录见 `VALIDATION.md`。接入真实资料后，再决定是否增加独立的客服工作台。
